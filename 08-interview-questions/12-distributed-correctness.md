# 分布式正确性与故障推演双角色练习

> [!NOTE] 案例性质说明
> 数字、输入数据和事故为教学推演；个人经历以履历事实清单为准。公开面经用于确认考点，追问与参考回答由本库整理。

## 1. 知识概述与业务价值

把“正确”写成可检查的不变量，例如每个退款请求只产生一次退款、旧状态不能覆盖新状态、订单与待发送事件同时提交。再逐个插入崩溃、重试、乱序和网络中断。

## 2. 核心概念与关系

投递次数、处理次数和业务副作用次数属于不同边界。幂等约束重复操作，版本约束更新顺序，事务约束同一边界内的原子性，补偿处理已经完成的跨边界动作。

## 3. 底层工作机制与设计哲学

超时后结果可能未知。重试要求相同业务身份与可重复执行语义；确认丢失会导致重复投递。每个协议都应明确状态保存在哪里、谁可以推进状态、故障后如何判断下一步。

## 4. 高频复杂业务场景实操与落地

画出请求接收、写业务行、写事件、提交、发消息、消费者提交、发送确认七个点。在每点前后模拟进程退出，填写已持久化数据、可能重复的动作与恢复入口。以下为教学协议；对应的应用进程崩溃、乱序和旧写约束已经在下述本地实验中验证。

| 故障点 | 已持久化的事实 | 恢复动作 | 验证标准 |
| --- | --- | --- | --- |
| 订单与 Outbox 提交前退出 | 两者都应未提交 | 按同一请求 ID 重试 | 只生成一次业务结果 |
| 提交后、发消息前退出 | 订单和事件均存在 | 转发器继续读取 | 事件最终到达 |
| 发消息后、确认发送前退出 | 发送结果可能未知 | 重发原事件 ID | 消费端去重生效 |
| 消费端业务提交后、位点确认前退出 | 业务和去重记录均存在 | 重收消息并返回已有结果 | 副作用次数保持一次 |
| 删除后重放旧更新 | 删除版本仍保留 | 拒绝旧版本 | 实体不会复活 |
| 旧持锁者暂停后恢复 | 新持有者已取得更高 fencing token | 资源原子拒绝旧 token | 新结果不被旧写覆盖 |

表中前四行假设业务变更与相应事件或去重记录在同一数据库事务中提交。若副作用在另一个服务，需额外验证该服务的幂等与查询契约。

### 已运行的故障注入与恢复结果

2026-11-24，使用 PostgreSQL 17.11 保存订单、Outbox、投递和消费状态。独立连接提交的投递表模拟消息系统，进程在精确断点被真实 SIGKILL 后恢复。[运行说明与源码入口](../code-demos/correctness-lab/README.md) · [原始结果](../code-demos/correctness-lab/results/2026-11-24-postgres17.json)

| 实际杀进程的位置 | 恢复前的数据库事实 | 恢复并重复消费后的结果 |
| --- | --- | --- |
| 订单与 Outbox 提交前 | 两者均为 0 条 | 订单与事件各 1 条，余额 10 |
| 订单提交后、转发前 | 订单与事件各 1 条，投递 0 条 | 投递 1 条，余额 10 |
| 投递持久化后、发送标记前 | 投递 1 条，消费尚未生效 | 投递增至 2 条，去重记录 1 条，余额 10 |
| 消费业务和去重写入后、提交前 | 余额 0，去重记录 0 条 | 去重记录 1 条，余额 10 |
| 消费提交后、确认前 | 余额 10，存在 1 条未确认投递 | 确认完成，余额仍为 10 |

另外，6 个同 ID、同参数请求并发提交只生成一个订单和事件；版本序列 v1、v2、旧 v1、v3 删除、旧 v2 最终保留 v3 墓碑；新 token 写入后旧 token 被拒绝。移除 fencing 校验的负例确实发生旧写覆盖。

**面试官追问：** 你说一次生效，为什么投递表有两行？

**求职者回答：** 这是实验观察到的重复发送。转发器来不及记录发送状态，恢复时会重发。消费端按事件 ID 去重，并把去重和余额变化放进同一个事务，两条投递只把余额从 0 改成 10。若把去重记录放 Redis、余额放数据库，就需要重新解决两个提交间隙。

**面试官追问：** 能证明 Kafka 和 Redis 在故障中都正确吗？

**求职者回答：** 本轮验证了应用进程崩溃时的事务边界。传输使用同一 PostgreSQL 上独立提交的表；fencing 使用数据库序列和条件更新。上述 13 项未启动 Kafka，也未注入 Redis 租约故障。后续补充的真实 Kafka 集成实验见下文；Redis 租约、宿主机断电和短信接口仍需另测。

### 真实 Kafka 故障与网络分区：5 项补充实测

本轮使用 Kafka 4.1.1 三个 KRaft 混合角色节点，单分区三副本、min ISR=2、acks=all。[实验源码与运行手册](../code-demos/kafka-fault-lab/README.md)包含六道双角色延伸题；[实测 JSON](../code-demos/kafka-fault-lab/results/2026-11-24-kafka411.json)保存选主、ISR、发送回调、位点和金额。

| 故障或对照 | 检查的事实 | 实测结论 |
| --- | --- | --- |
| 强杀实际分区 Leader | 退出码 137、非 OOM；ISR 从 3 降至 2 再恢复 3 | 新 Leader 接收写入，最终 40 个 ID、金额合计 400，无缺失 |
| Leader 网络隔离 | 进程仍运行，实验网络已断开；其余两节点选主 | 保留两个 ISR 时继续写入，恢复三副本后完整对账 |
| 隔离两个节点 | 发送回调超时，恢复后以相同业务 ID 重发 | 已观察到 41 条记录对应 40 个 ID；超时记录可能实际存在 |
| 消费库提交后、Kafka 位点提交前 SIGKILL | 库中已有金额 10，Kafka 尚无提交位点 | 恢复重读并命中一次去重，10 个业务 ID 最终金额 100，位点 10 |
| abort/commit 可见性 | 先 abort 5 条，再 commit 5 条 | read_committed 读 5 条，read_uncommitted 读 10 条 |

**求职者回答：** 我会把发送成功、日志存在、消费确认和业务生效分开核对。这次真实实验出现“发送超时、恢复后发现重复记录”，所以不能把超时当成没写入。外部业务去重需要同一事务内的唯一键和状态更新。

**面试官追问：** 那一条重复消息，Kafka 幂等为什么没挡住？

**求职者深入回答：** 恢复时创建了新 Producer，并重新提交相同业务 ID。这是应用重发，协议幂等不会根据业务 ID 自动去重。本次另用 SQLite 验证了真实消费提交间隙：数据库已提交而 Kafka 位点未提交，重读后跳过金额更新；这不等于已验证 Kafka 与远端 PostgreSQL 的联合故障。

**面试官追问：** 进程活着就能算服务恢复了吗？

**求职者深入回答：** 不能。首轮网络隔离时，新 Leader 已出现，但原客户端仍报交付超时。脚本明确连接探测、元数据刷新和交付预算后重跑通过。应该分别检查集群选主、客户端发送成功和业务积压追平。

**架构师视角：** 当前混合角色部署隔离两个节点时，也失去 Controller 多数派，不能把拒写只归因于 min ISR。发布验收应分别测控制面和数据面，按租户限制重试与积压。保留业务 ID 对账，恢复后逐项检查；本机少量输入不提供生产容量或 P99 结论。

## 5. 生产异常故障深度排查与根因分析

重复扣款 → 查幂等键及其事务边界。状态倒退 → 查版本及回填覆盖。丢事件 → 查业务提交与消息发布的间隙。旧持锁者写入 → 查租约与资源端校验。一直不一致 → 查补偿积压、日志保留和人工处置流程。

## 6. 技术选型对比、架构演进与成本ROI

同库事务简单但边界有限；Outbox 增加表、转发与重复处理成本；Saga 需要可执行且幂等的补偿。强同步确认增加等待，异步传播需明确可见延迟和对账责任。共识只能解决其协议边界内的协调，外部副作用仍需约束。

## 7. 技术经理与架构师实战管控

对关键业务记录稳定请求 ID、源版本和处理结果，监控去重冲突、重试量、事件年龄与补偿失败。按租户限流，维护有界重试与告警，恢复后验证业务不变量。

## 9. 结构化深度参考答案

### 题目1　接口超时后如何安全重试？

#### 简洁回答

**求职者**　使用稳定业务请求 ID，在唯一约束下记录请求参数与结果，重复请求查询同一操作结果。

#### 深入回答

**面试官**　先在 Redis 放一个成功标志，再写数据库可以吗？

**求职者**　中间崩溃会留下标志却未执行业务。同库可把去重记录与业务变更放在同一事务；进行中状态需有恢复协议，相同 ID 不同参数应拒绝。跨服务需依赖下游幂等键与结果查询。

#### 架构师/技术管理视角

幂等保留期覆盖最长合法重试时间。记录技术失败、业务拒绝和未知结果的区别，避免把失败永久缓存为成功。

### 题目2　订单提交和发送消息如何避免双写丢失？

#### 简洁回答

**求职者**　同一数据库事务写订单与 Outbox 事件，提交后转发器读取事件发送到消息系统。

#### 深入回答

**面试官**　消息发出后，标记发送成功之前宕机呢？

**求职者**　事件会重发，所以消费者仍需按事件 ID 去重。同库消费副作用与消费记录可以原子提交；发送状态不能证明远端业务已完成。逐实体版本帮助处理顺序。

#### 架构师/技术管理视角

清理事件前确认可恢复依据，监控事件年龄与重发率，准备死信重放并保留原事件 ID。

### 题目3　更新乱序、历史补数与删除如何兼容？

#### 简洁回答

**求职者**　按实体键使用可靠源版本，只接受业务允许的新版本。补数写入也携带可比较版本，删除有相应版本或墓碑。

#### 深入回答

**面试官**　删除后清掉所有状态，旧事件重放怎么办？

**求职者**　旧数据可能复活。墓碑或去重信息的保留需覆盖重放窗口；超出保留期要从可信基线恢复。不同源序号不可直接比较，应定义字段归属或业务冲突规则。

#### 架构师/技术管理视角

批量回填先隔离计算并对账，切换前处理增量追平。快照正确还需验证下游汇总能撤回旧值。

### 题目4　分布式锁过期后，旧客户端还在执行怎么办？

#### 简洁回答

**求职者**　锁租约过期允许新持有者进入，但旧客户端可能从暂停中恢复继续写。需要资源端拒绝过期持有者。

#### 深入回答

**面试官**　用随机 token 比较后删除锁够了吗？

**求职者**　随机 token 防止误删别人的锁。防旧写需单调递增的 fencing token，并由实际资源持久化、原子校验。资源不支持该机制时，可采用条件版本更新等可验证约束；续租也有暂停和故障边界。

#### 架构师/技术管理视角

选型先明确资源是否能校验 token，设计长暂停与网络中断演练，不能只测正常加锁解锁。

### 题目5　Kafka 事务能保证数据库和短信也只执行一次吗？

#### 简洁回答

**求职者**　Kafka 事务可协调其边界内的消息及消费位点；外部数据库和短信需各自的原子或幂等协议。

#### 深入回答

**面试官**　数据库已提交，位点还没提交就宕机呢？

**求职者**　消息会再处理。可在数据库事务内写事件 ID 去重记录和业务结果，再确认位点；若先确认位点再写库，崩溃可能丢业务处理。短信接口需支持幂等或查询确认，数据库标记本身不能替短信服务保证一次。

#### 架构师/技术管理视角

演练每个提交间隙，用最终业务结果验证，分别记录重复投递与重复副作用。

### 题目6　数据库更新后缓存仍是旧值，怎样处理？

#### 简洁回答

**求职者**　先定义可接受陈旧时间。可在数据库提交后失效缓存，并用可靠事件补偿失效失败，TTL 限制部分陈旧窗口。

#### 深入回答

**面试官**　删除缓存后，一个旧查询刚好把旧值写回呢？

**求职者**　存在读写竞争。可以使用业务版本并在缓存端原子拒绝旧版本覆盖，或在适合场景绕过缓存读权威源。删除版本记录会削弱防旧写能力；延迟双删的时间假设无法覆盖任意长暂停。

#### 架构师/技术管理视角

按业务选择强读取、短暂陈旧或版本校验，监控补偿积压与陈旧年龄。避免大量缓存同时过期冲击数据库。

技术机制核对入口。[Kafka 设计](https://kafka.apache.org/37/design/design/) · [Redis 分布式锁](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) · [事务 Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
